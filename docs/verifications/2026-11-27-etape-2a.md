## 3. Anomalies

### A1. Double soumission de la création : deux fiches (majeure)

- **Preuve** :
  - deux POST identiques sur `/gestion/personnes/nouvelle/`, même session et même jeton CSRF ;
  - réponses : `post1 303 …/personnes/34/` et `post2 303 …/personnes/35/` ;
  - en base : `34 Doublon Verif 77 123 45 67 to_reconcile=0 created_by=2` et `35 Doublon Verif 77 123 45 67 to_reconcile=0 created_by=2`.
- **Cause** :
  - `PersonneController::store()` (`app/Controllers/Gestion/PersonneController.php:68` à `:123`) n'a ni jeton à usage unique ni contrainte d'unicité ;
  - le jeton CSRF de session est réutilisable ;
  - sans e-mail, `emailConnu()` ne marque même pas la seconde fiche « à rapprocher ».
- **Exigence non tenue** : `docs/gestion-plan.md` §10, « Double soumission (double clic, retour arrière) : aucun doublon en base ».
- **Correctif suggéré** :
  - jeton de formulaire à usage unique, consommé dans `store()` (la seconde soumission redirige vers la fiche déjà créée) ;
  - désactivation du bouton à l'envoi, en complément seulement ;
  - un test dans le robot.

### A2. Compteur « Dossiers » de la liste hors périmètre (mineure)

- **Preuve** :
  - `app/Models/Person.php:125` : `(SELECT COUNT(*) FROM service_requests r WHERE r.person_id = p.id) AS dossiers`, sans `Access::perimetre()` ;
  - affiché dans `app/Views/gestion/personnes.php:44` ;
  - constat pour l'agent d'orientation « Une » sur la fiche 32 : **2** dossiers dans la liste, mais `Dossiers 1` sur la fiche (seul `TAY-RCT-000003` est dans son périmètre).
- **Effet** : révèle l'existence d'un dossier hors périmètre (un nombre seulement, aucun contenu). Le compteur `rendez_vous` (`:126`) est lui aussi global.
- **Correctif suggéré** : compter avec la même condition que `Person::dossiers()` (`Access::perimetre($user, 'r')`), ou retirer la colonne.

### A3. Fiche orpheline possible dans `Person::pourCompte()` en cas d'appels concurrents (mineure)

- **Preuve** :
  - `app/Models/Person.php:57` à `:68` : création de la fiche, puis `UPDATE users SET person_id = ? … WHERE id = ? AND person_id IS NULL` ;
  - le résultat de l'`UPDATE` n'est pas vérifié et la fiche neuve est retournée dans tous les cas.
- **Effet** :
  - deux premières actions simultanées d'un compte sans fiche créent deux fiches, dont une seule est liée au compte ;
  - la demande ou le rendez-vous rattaché à l'autre ne s'affiche pas dans `/mon-espace/` : `CLIENT_SCOPE` compare au `person_id` du compte, et le secours `user_id` ne joue que si `person_id IS NULL`.
- **Portée** : cas étroit, puisque la reprise 011 et l'inscription créent la fiche d'avance. Non reproduit, déduit du code.
- **Correctif suggéré** : si l'`UPDATE` n'affecte aucune ligne, relire `users.person_id` et retourner cette fiche (ou verrouiller la ligne du compte).

### A4. Retour arrière : fiches créées après 011 perdues sans garde-fou (mineure)

- **Preuve** :
  - `database/rollback/011_personnes.down.sql:19` : `DROP TABLE IF EXISTS people;` ;
  - le seul garde-fou (ligne 7) porte sur les dossiers sans compte.
- **Effet** : des fiches créées par l'équipe (origine `visite`, `prospect`), sans dossier ni compte, disparaissent sans avertissement lors d'un retour arrière.
- **Correctif suggéré** : ajouter un second garde-fou (erreur 1242) s'il existe des fiches `origin <> 'reprise'` sans compte, ou au moins le documenter dans l'en-tête du script et dans `docs/deploiement-vps.md`.

### A5. K4 « ou un rendez-vous » non couvert par `personnesSql()` (mineure, écart assumé)

- **Preuve** : `app/Services/Access.php:313`, « Les rendez-vous attribués à un membre s'ajouteront en 2B ».
- **Constat** : K4 et le plan 2A prévoyaient les personnes « dont ils tiennent un dossier ou un rendez-vous ». Les rendez-vous n'ont pas encore de responsable, la règle ne peut donc pas s'appliquer.
- **Correctif suggéré** : le reporter explicitement dans le plan de 2B, avec un contrôle P4 bis sur les rendez-vous.

### Observations sans gravité

- **Rendez-vous de la fiche** : `Person::rendezVous()` (`app/Models/Person.php:146`) liste tous les rendez-vous d'une personne visible, sans filtre propre. C'est cohérent avec la règle « fiche visible, donc contenu de la fiche visible », mais à revoir en 2B quand les rendez-vous auront un responsable.
- **Recherche pour la prospection et la commerciale** : `/gestion/recherche/` (route `acces:gestion`) leur répond 200 avec une liste vide, sans fuite. La palette ne leur est pas affichée.
- **Existence d'une fiche** : un 403 sur une fiche existante, contre un 404 sur une fiche inexistante, révèle l'existence d'un identifiant. Ce choix est voulu et commenté (`PersonneController.php`), pour journaliser la tentative.
- **Bases de recette restantes** : `taysir_1239d6ecaf974f7e_recette` et `taysir_5ef1de0dc48b45ff_recette` existent dans MySQL local. Leur format de nom diffère de celui des outils actuels. Je ne les ai pas créées et je ne les ai pas supprimées.
- **Exit code des outils** : la tâche de fond qui enchaînait les deux répétitions a fini avec le code 1, alors que chaque outil a écrit `exit 0` dans son journal. Le 1 vient de la commande `tail` finale du lanceur, pas des outils.
